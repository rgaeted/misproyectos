# Pagos por proyecto: plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cada proyecto tiene planes de pago en UF (único, cuotas o mensual). Las fechas se generan solas, cada pago se marca como pagado con un clic, se ve el equivalente en pesos y hay una vista general de cobros.

**Architecture:**
- Los planes se guardan en `payment_plans`. Los pagos pendientes no se guardan: se calculan con lógica pura en `lib/payments.ts`. Solo se guarda un registro en `payments` cuando un pago se marca como pagado, junto con el monto en UF y el valor de la UF de esa fecha.
- El valor de la UF sale de mindicador.cl (`lib/uf.ts`). Si falla, devuelve `null` y la UI muestra solo UF.
- Las mutaciones siguen el patrón `mutate({ op })` de `lib/actions.ts`. Los datos se cargan en `getBoard`.

**Tech Stack:** Next.js 15, React 19, Drizzle 0.44 + Postgres con RLS, zod 4, vitest.

**Spec:** `docs/superpowers/specs/2026-11-07-pagos-design.md`

## Global Constraints

- Moneda: UF, con 2 decimales. Formato de UF: `"9,00 UF"`. Formato de pesos: `"$ 342.150"` (sin decimales, punto de miles, locale `es-CL`).
- "Hoy" siempre es la fecha en `America/Santiago`. Las fechas se manejan como strings `YYYY-MM-DD`; no se usan objetos `Date` para comparar días.
- Los pagos caen el mismo día del mes que `startDate`. Si ese día no existe en el mes, caen el último día del mes. El día ancla se mantiene: 31 ene → 28 feb → 31 mar.
- "Por cobrar" de un plan mensual llega hasta hoy + 12 meses. Las cuotas y el pago único se muestran completos.
- Fecha de pago = la más temprana entre hoy y la fecha del pago.
- Un pago ya pagado nunca cambia de monto por editar el plan. Si queda fuera del calendario, se sigue mostrando en "Pagado".
- Los pendientes de proyectos archivados no aparecen en la vista general. Lo cobrado en ellos sí cuenta en "Cobrado en el año".
- Todo el texto de la UI va en español de Chile, en el mismo tono que el resto de la app.
- Cada tabla nueva lleva RLS con la misma política "existe el proyecto del usuario" que `project_steps`, más `FORCE ROW LEVEL SECURITY`.

## Review Focus

1. **Fin de mes y día ancla:** con un plan que parte el 31 de enero, los pagos caen 28/29 feb, 31 mar, 30 abr. No se corren al día 28 para siempre. (Task 1)
2. **Plan editado con pagos fuera del calendario:** pasar de 4 a 3 cuotas con la cuota 4 pagada la deja en "Pagado", no en "Por cobrar", y el total cobrado no cambia. (Task 1)
3. **Medianoche en Chile:** a las 01:30 UTC del 1 de diciembre, en Chile todavía es 30 de noviembre. Un pago que vence el 30 de noviembre aún no está atrasado. (Task 1)
4. **API de la UF caída o con respuesta rara:** `fetchUf` devuelve `null` sin lanzar error, y marcar como pagado funciona igual, con `ufValue = null`. (Tasks 2 y 4)
5. **Doble clic en "Marcar pagado":** no da error ni duplica el registro, gracias a `unique(plan_id, seq)` y `onConflictDoNothing`. (Task 4)

```ts
export const planKinds = ["once", "installments", "monthly"] as const;
export type PlanKind = (typeof planKinds)[number];
export const planKindLabels: Record<PlanKind, string>; // "Pago único", "Cuotas", "Mensual"
export type PaymentPlan = { id: string; projectId: string; concept: string; kind: PlanKind;
  amountUf: number; startDate: string; installments: number | null; endDate: string | null; position: number };
export type PaidPayment = { id: string; planId: string; seq: number; dueDate: string;
  amountUf: number; paidOn: string; ufValue: number | null };
export type ScheduleEntry = { planId: string; seq: number; dueDate: string; amountUf: number };
export type PaymentRow = ScheduleEntry & { concept: string; status: "paid" | "pending" | "overdue";
  paidOn: string | null; ufValue: number | null };
export function todayInChile(now?: Date): string;                 // "YYYY-MM-DD" en America/Santiago
export function addMonths(startDate: string, months: number): string; // ancla = día de startDate, recorta a fin de mes
export function dueDateFor(plan: PaymentPlan, seq: number): string | null; // null si seq no existe en el plan
export function planSchedule(plan: PaymentPlan, until: string): ScheduleEntry[];
export function projectPayments(plans: PaymentPlan[], paid: PaidPayment[], today: string):
  { paid: PaymentRow[]; upcoming: PaymentRow[]; totalPaidUf: number };
export function paymentsOverview(projects: { id: string; name: string; archived: boolean; plans: PaymentPlan[]; payments: PaidPayment[] }[], today: string): {
  thisMonth: { totalUf: number; rows: (PaymentRow & { projectId: string; projectName: string })[] };
  nextMonth: { totalUf: number; rows: (PaymentRow & { projectId: string; projectName: string })[] };
  overdue:   { totalUf: number; rows: (PaymentRow & { projectId: string; projectName: string })[] };
  collectedYear: { uf: number; clp: number; clpComplete: boolean };
};
export function paidOnFor(dueDate: string, today: string): string; // min(dueDate, today)
export function formatUf(value: number): string;   // "9,00 UF"
export function formatClp(value: number): string;  // "$ 342.150"
export function ufToClp(uf: number, ufValue: number): number; // Math.round(uf * ufValue)
```

Reglas que los tests fijan:
- `dueDateFor(plan, seq) = addMonths(plan.startDate, seq)`. Es válido para `once` si `seq === 0`, para `installments` si `seq < installments` y para `monthly` si `endDate === null` o la fecha es `<= endDate`.
- `planSchedule` con `until` solo limita a `monthly`.
- En `projectPayments`, `paid` sale de los registros pagados (no del calendario), ordenado por `dueDate` ascendente. El `concept` se toma del plan.
- En `projectPayments`, `upcoming` son las entradas de `planSchedule(plan, addMonths(today, 12))` sin registro pagado. Una entrada con `dueDate < today` es `overdue`. Las atrasadas van primero y luego todo por fecha ascendente.
- `paymentsOverview`:
  - "Este mes" y "el próximo mes" se definen por el prefijo `YYYY-MM` de la fecha de vencimiento e incluyen solo pendientes no atrasados.
  - "Atrasados" son los `overdue`.
  - Se excluyen los proyectos archivados de esas tres listas.
  - `collectedYear` suma los pagados con `paidOn` en el año de `today`, incluyendo archivados. `clp` suma solo los que tienen `ufValue`, y `clpComplete` es `false` si a alguno le falta.

**Interfaces:**

- Produces: nuevas variantes de `command`. `CommandInput` se actualiza solo.
```ts
{ op: "addPlan", projectId: string, concept: shortText, kind: PlanKind, amountUf: number, startDate: string, installments?: number }
{ op: "editPlan", id: uuid, concept?: shortText, amountUf?: number, startDate?: string, installments?: number, endDate?: string | null }
{ op: "deletePlan", id: uuid }
{ op: "markPaid", planId: uuid, seq: number }
{ op: "unmarkPaid", planId: uuid, seq: number }
```
Reglas:
- `amountUf`: número `> 0`, `<= 100000`, con un máximo de 2 decimales. Mensaje: "Usa un monto en UF mayor que 0, con hasta 2 decimales."
- Fechas: regex `^\d{4}-\d{2}-\d{2}$` y fecha real. Mensaje: "Usa una fecha válida."
- `installments`: entero de 2 a 120, obligatorio solo si `kind === "installments"` y prohibido en los otros tipos. Mensaje: "Indica entre 2 y 120 cuotas."
- `seq`: entero de 0 a 10000.
- `editPlan` necesita al menos un campo (mensaje "Indica qué quieres cambiar.").
- En el servidor:
  - `installments` solo se acepta en planes de cuotas y `endDate` solo en mensuales.
  - `endDate` debe ser `>= startDate`. Para guardarlo, se normaliza con `dueDateFor`: se guarda la fecha de pago del mes elegido. La UI manda la fecha de pago elegida en un select.
- Hay un máximo de 50 planes por proyecto.

Comportamiento en `lib/actions.ts`:
- Agrega un helper `ownedPlan(id)` dentro de la transacción, con el patrón de `ownedStep`: el plan existe y `ownedProject(plan.projectId)` lo confirma.
- `addPlan`: inserta con `position = max + 1`.
- `editPlan`: actualiza solo los campos que llegan.
- `deletePlan`: borra el plan; los pagos se borran en cascada.
- Todas estas operaciones hacen `touch(projectId)`.
- `markPaid` se hace en dos fases, como `refresh`, para no tener abierta la transacción durante la llamada HTTP:
  1. Con `withUserDatabase`, lee el plan dueño y calcula `dueDate = dueDateFor(plan, seq)`. Si es `null`, lanza `invalid_payment`.
  2. Calcula `paidOn = paidOnFor(dueDate, todayInChile())`.
  3. Obtiene `ufValue`: si `paidOn` es hoy, con `getUfToday()`; si no, con `fetchUf(paidOn)`.
  4. Con un segundo `withUserDatabase`, inserta `{ planId, seq, dueDate, amountUf: plan.amountUf, paidOn, ufValue }` con `.onConflictDoNothing()` y hace `touch`.
- `unmarkPaid`: con `ownedPlan`, borra `payments` por `planId + seq` y hace `touch`. Si no hay fila, no es error.
- Las mutaciones nuevas terminan en el `revalidateTag` / `revalidatePath` existentes.
